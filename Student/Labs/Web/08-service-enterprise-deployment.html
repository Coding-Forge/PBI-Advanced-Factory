Lab 8 - Publish and distribute

Service Enterprise Deployment

Publish your Power BI file to the Service, configure refresh, review gateways, shared semantic models, Apps, App audiences, deployment pipelines, and endorsement.

OperationsDeliverable: Published workspace/App planPower BI file

What you will produce

  • Workspace design and roles
  • Refresh and gateway notes
  • App packaging
  • Endorsement checklist

Step-by-step walkthrough

  1. Open the training workspace and record the deployment plan.
    1. In Power BI Service, click Workspaces in the left navigation, then open the workspace you will use for this lab.
    2. At the top of the workspace, record whether this workspace represents development, test, production, or a training-only environment.
    3. Click Access and confirm your own workspace role before you continue.
    4. Write down the workspace naming convention, domain or subject area, content owner, and support owner.
    5. Decide the least-privileged role each collaborator should receive: Admin, Member, Contributor, or Viewer.

    Use the checklist below as the working reference for the rest of the lab so you capture the same configuration, permissions, and evidence in one place.

    FYI — why workspace role selection matters.

    This is where day-to-day governance starts. Admin can manage the workspace and access, Member can publish and update App content, Contributor can create and update content without fully administering the workspace, and Viewer can consume content only. If too many people get Member or Admin, support and change control quickly become unclear.

  2. Publish the report from Power BI Desktop.
    1. Open the same Power BI file you completed through Lab 07 (including static/dynamic RLS) in Power BI Desktop. Do not start a new file.
    2. Confirm you are signed in with the approved training account.
    3. On the Home ribbon, click Publish.
    4. In the publish dialog, select the target training workspace, then click Select.
    5. Wait for the publish confirmation, then click the option to open the item in the Service or switch back to the browser and open the workspace.
    FYI — publish is not the same as sharing.
    Publishing from Power BI Desktop creates or updates the report and semantic model inside a workspace so the team has a governed source to manage. Sharing a direct link is more ad hoc, while publishing an App later gives consumers a curated navigation experience without granting them workspace authoring access.
  3. Verify the report and semantic model in the Service.
    1. In the workspace content list, confirm the published report appears.
    2. In the same list, confirm the matching semantic model appears.
    3. Open the report once to confirm it loads in the browser.
    4. Record the workspace name, report name, semantic model name, and owner details in your notes.
  4. Open the semantic model settings page.
    1. Return to the workspace content list.
    2. Locate the semantic model that was published with the report.
    3. Click the semantic model More options menu (...), then click Settings.
    4. Review the owner field, data source credentials section, privacy level setting, and refresh history area.
  5. Review credentials and scheduled refresh where supported.
    1. On the settings page, expand Data source credentials.
    2. For each source, click Edit credentials or confirm the existing credentials and privacy settings.
    3. Expand Scheduled refresh, turn the schedule on if your tenant allows it, then choose the required frequency, time zone, and notification recipients.
    4. Click Apply or Save if you made changes.
    5. Run a manual refresh and return to Refresh history to confirm the result before you rely on the schedule.

    If the training tenant blocks one of these options, document the exact blocker instead of forcing the change.

    FYI — why refresh validation comes before go-live.
    A published semantic model is only useful if the Service can authenticate to every source on a schedule. Refresh history tells you whether credentials, privacy settings, source access, or a gateway/cloud connection are working in practice, which is why a successful manual refresh is better evidence than just seeing the schedule turned on.
  6. Document whether a gateway or cloud connection is required.

    Review the lab's data sources and note whether they are public cloud URLs or on-premises or network-restricted sources. For this workshop's public GitHub-hosted CSV pattern, record that no gateway is required. If a gateway-backed source were introduced later, capture the expected gateway cluster, data source mapping, credential owner, and network path before enabling refresh.

  7. Review the shared semantic model and thin-report pattern.
    1. From the semantic model menu in the Service, open Manage permissions or the permissions page available in your tenant.
    2. Confirm the intended analyst or group has Build permission, or document that this permission must be granted by the model owner.
    3. In Power BI Service or Power BI Desktop, choose the option to create a new report from an existing Power BI semantic model.
    4. Select the published semantic model, create a simple thin report, and save or publish it back to the workspace if your environment allows it.

    Record why the shared-model pattern separates semantic model governance from report authoring.

    FYI — why Build permission matters.
    Build is what allows another author to create a new report from this published semantic model without giving them full ownership of the model itself. That separation is important because it lets one team govern calculations, RLS, and refresh centrally while other teams create thin reports that stay consistent with the same trusted data definition.
  8. Package the workspace content as an App.
    1. Return to the workspace and click Create app or Update app.
    2. On the Setup tab, enter the App name, description, and any branding fields used in your tenant.
    3. On the Navigation tab, choose which reports or pages appear and arrange them in the order consumers should see them.
    4. On the Audience tab, add the intended users or security group.
    5. Click Publish app or Update app, then open the app link to validate the consumer experience.
    FYI — why distribute through an App instead of the workspace.
    The workspace is the authoring and administration area; the App is the polished consumer-facing package. Publishing the App lets you control navigation, audience membership, and what end users see, while the workspace can still hold drafts, support artifacts, or content that should stay hidden from consumers.
  9. Review App audiences if the tenant supports them.
    1. While editing the App, stay on the Audience tab.
    2. Add another audience if the feature is available in your tenant.
    3. Assign different content or navigation options to that audience and save the changes.

    If multiple audiences are not available or not validated in Azure Government for this tenant, mark the feature Verify for Gov in your notes and keep the hands-on portion optional.

  10. Review deployment pipelines or document the manual promotion path.
    1. If deployment pipelines are enabled, open Deployment pipelines from the workspace or Service navigation.
    2. Create or open a pipeline, then map the Development, Test, and Production workspaces.
    3. Review any deployment rules, such as different parameters or connections by stage, before promoting content.
    4. Deploy to the next stage only if your instructor or tenant permissions allow it.

    If pipelines are unavailable, write down the manual promotion sequence you would use instead, such as reviewed republish from your Power BI file into each workspace in order.

    FYI — why deployment pipelines use Development, Test, and Production stages.
    Pipelines reduce the risk of treating production as the first place content is tested. Stage-specific rules let you keep the same report and semantic model design while swapping items like parameters or connections by environment, so promotion is more repeatable than manually republishing and hoping every setting matches.
  11. Complete the endorsement governance review.
    1. Return to the semantic model or report settings page and identify the endorsement option available in your tenant.
    2. Gather evidence for ownership, refresh reliability, security configuration, data quality, and support readiness.
    3. Decide whether the item is only eligible for Promoted or is ready for Certified, based on your governance policy.
    4. Record the evidence and any gaps in your lab notes, even if endorsement changes cannot be made in the training tenant.
    FYI — why endorsement affects trust and discoverability.
    Promoted signals that a content owner recommends the item for broader reuse, while Certified usually means it has passed a formal governance review. In a large tenant, that distinction helps analysts find the semantic models and reports that are most likely to be accurate, supported, and safe to build on.

Azure Government note

Use the Gov-ready path by default. Features marked Verify for Gov or Commercial-focused require tenant, licensing, capacity, network, identity, or policy validation before hands-on delivery.
