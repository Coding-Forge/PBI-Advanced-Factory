    FYI — what is filter context?
    Every cell in a visual (each row, column, subtotal, or grand total) applies its own combination of filters from slicers, rows, columns, and page/report filters. A measure re-evaluates for each of those combinations. That is why the same [Sales Amount] measure can show a different number in every cell of the matrix — it is not one calculation, it is one formula evaluated many times, once per filter context.
  4. Create a row-context-only example, then compare it to measures.

    Create one small calculated column example only to demonstrate row context, review why it evaluates row by row, then return to measures for report aggregations so learners can see why measures are the preferred pattern for reusable analytics.

    FYI — row context vs. filter context.
    A calculated column evaluates once per row of its own table (row context) and that value is stored permanently in the model. A measure has no fixed row — it recalculates on demand using whatever filter context the visual currently applies. Use calculated columns sparingly (for slicer/axis fields), and prefer measures for anything that should react to slicers, so your model stays flexible and refresh times stay predictable.
  5. Create CALCULATE measures that intentionally change filters.
    1. Select your measure table and click Modeling > New measure.
    2. Create a measure that removes product filters so you can compare filtered sales to all-product sales.
    3. Create a product-share measure that divides current sales by the unfiltered product total.
    4. Create a measure that uses KEEPFILTERS to narrow the calculation to a selected customer type without replacing other filters.
    5. Test each measure in the same matrix and slicers before you reuse it anywhere else.

    Discuss the intent of REMOVEFILTERS, ALL, ALLEXCEPT, and TREATAS while you test so learners choose filter modifiers deliberately instead of by trial and error.

    FYI — why CALCULATE and its filter modifiers matter.

    CALCULATE is the only DAX function that can change filter context — every filter modifier below is really just an argument to CALCULATE. Knowing which one to reach for keeps a measure predictable instead of "trial and error":

    • CALCULATE evaluates an expression in a new filter context that you define — it is the mechanism behind almost every advanced measure in this lab.
    • REMOVEFILTERS(<table or column>) clears filters from just the table/column you name, so the rest of the report's filters (region, date, etc.) still apply. Use it when you need one dimension to stop filtering without losing every other slicer.
    • ALL(<table or column>) behaves like REMOVEFILTERS in most measures but also changes row context for iterators — use it when you need an unfiltered total to compare against (like a percent-of-total).
    • ALLEXCEPT(<table>, <column(s)>) removes every filter on a table except the column(s) you list. It is a shortcut for "clear everything on this dimension except one attribute" instead of writing several REMOVEFILTERS calls.
    • KEEPFILTERS(<condition>) adds a filter without replacing the existing one on that column. Without it, a hardcoded condition like DimCustomer[CustomerType] = "Enterprise" would overwrite (not intersect with) whatever the user already sliced — so results would stop respecting other active slicers.
    • TREATAS(<table>, <columns>) applies the values of one table as a filter on columns in another table, even when there is no physical relationship. Reach for it for virtual relationships (e.g., filtering by a disconnected selector table) instead of adding a real, always-on relationship.

    FYI — why time intelligence needs a marked date table.
    Functions like TOTALYTD, SAMEPERIODLASTYEAR, and DATESINPERIOD only work correctly against a contiguous, one-row-per-day date table that Power BI recognizes as a Date table (Model view > table > "Mark as date table"). Using a raw transaction date column instead can silently skip dates with no sales, breaking prior-year and rolling-window math. That is why step 1 confirms DimOrderDate before you write any of these measures.
  7. Review a semi-additive pattern before you sum snapshot-style data.

    Discuss why inventory, backlog, headcount, or balance snapshots should not be summed across dates. Create or review an ending-balance or last-nonblank pattern from the answer key so learners can recognize when a last-value calculation is required.

    FYI — additive vs. semi-additive measures.
    Sales Amount is additive: summing across dates gives a meaningful total (total sales for the quarter). A snapshot value like inventory-on-hand or headcount is semi-additive: it can be summed across products or locations, but summing it across dates produces a meaningless number (you would be adding the same warehouse's balance to itself on different days). The fix is to pick one representative day's value — usually the last day in the selected period — with a pattern such as CALCULATE([Balance], LASTDATE(DimDate[Date])) instead of SUM.

    1. Create Customer Sales Rank with RANKX over DimCustomer[CustomerName].

    3. Add a customer bar chart that uses [Sales Amount].
    4. Drag [Is Top 5 Customer] into the visual-level filters and keep only the Top 5 result.

    Item to createExact namePattern or fieldsValidation
    Ranking measureCustomer Sales RankRANKX(ALLSELECTED(DimCustomer[CustomerName]), [Sales Amount], , DESC, DENSE)Rank respects slicers.
    Flag measureIs Top 5 CustomerIF([Customer Sales Rank] <= 5, 1, 0)Returns 1 only for the current Top 5.
    FYI — why RANKX uses ALLSELECTED, not ALL.
    RANKX needs a list of customers to rank against. If you used ALL(DimCustomer[CustomerName]), the rank would always be computed against every customer in the model, ignoring any slicer the report user applied. ALLSELECTED instead ranks against whatever customers are currently visible after slicers are applied, so "rank 1" always means "top of what I'm looking at right now" — the behavior most report users expect.

    FYI — why SELECTEDVALUE needs a fallback.
    SELECTEDVALUE(<column>, <alternate result>) returns the single selected value only when exactly one value is in context. With zero or multiple values selected (nothing picked, or a multi-select slicer) it returns the alternate result instead of blank or an error. Always supply a readable fallback such as "All Regions" or "Multiple Selections" so the title never looks broken in front of a stakeholder.
    FYI — why MetricSelector must stay disconnected.
    If MetricSelector had a relationship to another table, Power BI would try to use it to filter the model, which is not what you want — it exists only so a slicer can read its MetricName values. The SWITCH measure is what actually reacts to the slicer, by checking which row is selected and returning a different existing measure each time. This "disconnected table + SWITCH" pattern is the standard way to let a report user change which metric a visual displays without duplicating every visual once per metric.
  10. Review calculation groups only on a validated authoring path.
    1. Confirm your base measures work before you add any calculation group logic.
    2. Open Model view.
    3. On the ribbon, click Calculation group.
    4. If prompted, enable Discourage implicit measures.
    5. Rename the calculation group table to Time Intelligence, rename the column to Time Calculation, and rename the first item to Current.
    6. Set the Current expression to SELECTEDMEASURE(), then add items such as Prior Year, YoY Change, and YoY Change %.
    7. Test Time Intelligence[Time Calculation] against [Sales Amount] and [Gross Margin] in a visual.

    This path is Verify for Gov. Review TMDL View, Tabular Editor, XMLA, or CI/CD workflows only when the customer environment supports them; otherwise compare the design to separate DAX measures.

    FYI — why calculation groups instead of more measures.
    Without a calculation group, showing "Prior Year", "YoY Change", and "YoY Change %" for every base measure (Sales Amount, Gross Margin, etc.) means writing 3 extra measures per base measure — the count multiplies fast. A calculation group defines the time-intelligence logic once with SELECTEDMEASURE() as a placeholder, and it applies that logic to whichever measure a report author drops into the visual, so the measure list stays small and consistent.
  11. Refactor, validate, and document the final measure layer.
    1. Rewrite any repeated logic with variables.
    2. Confirm derived measures branch from existing base measures instead of repeating SUM logic.
    3. Check totals at customer, product, territory, and date grain.
    4. Review formatting, descriptions, and fallback behavior before the measures are reused on report pages.
    5. If you use DAX Studio or another external tool, label that path Verify for Gov unless the environment has already been validated.
    FYI — why VAR/RETURN and base-measure reuse matter.
    A VAR stores an expression's result once so DAX does not recompute it every time it is referenced later in the same measure — this improves both readability and performance in patterns like Sales Rolling 90 Days. Likewise, building Sales Variance from [Sales Amount] - [Target Sales Amount] (existing measures) instead of retyping the underlying SUM expressions means a future change to the base logic (a new filter, a bug fix) automatically flows through every measure built on top of it.

Calculation group answer key

Use these formulas for the Time Calculation calculation items. Each item uses SELECTEDMEASURE() so the same logic can apply to multiple explicit base measures.

// Current
SELECTEDMEASURE()

// MTD
CALCULATE (
    SELECTEDMEASURE(),
    DATESMTD ( DimOrderDate[Date] )
)

// QTD
CALCULATE (
    SELECTEDMEASURE(),
    DATESQTD ( DimOrderDate[Date] )
)

// YTD
CALCULATE (
    SELECTEDMEASURE(),
    DATESYTD ( DimOrderDate[Date] )
)

// Fiscal YTD
CALCULATE (
    SELECTEDMEASURE(),
    DATESYTD ( DimOrderDate[Date], "6/30" )
)

// Prior Year
CALCULATE (
    SELECTEDMEASURE(),
    SAMEPERIODLASTYEAR ( DimOrderDate[Date] )
)

// YoY Change
VAR PriorYearValue =
    CALCULATE (
        SELECTEDMEASURE(),
        SAMEPERIODLASTYEAR ( DimOrderDate[Date] )
    )
RETURN
    SELECTEDMEASURE() - PriorYearValue

// YoY Change %
VAR PriorYearValue =
    CALCULATE (
        SELECTEDMEASURE(),
        SAMEPERIODLASTYEAR ( DimOrderDate[Date] )
    )
RETURN
    DIVIDE ( SELECTEDMEASURE() - PriorYearValue, PriorYearValue )

// Rolling 90 Days
VAR LastVisibleDate =
    MAX ( DimOrderDate[Date] )
RETURN
    CALCULATE (
        SELECTEDMEASURE(),
        DATESINPERIOD ( DimOrderDate[Date], LastVisibleDate, -90, DAY )
    )
