Lab 10 - Architecture decisions

Premium, Fabric, and Capacity

Compare Pro, PPU, Premium, and Fabric capacity and evaluate XMLA, paginated reports, Direct Lake, OneLake, Semantic Link, capacity metrics, and Gov-safe alternatives.

ArchitectureDeliverable: Capacity architecture recommendationPower BI file

What you will produce

  • Capacity comparison
  • XMLA/paginated/large-model validation
  • Fabric feature validation
  • Gov-safe architecture
  • Capacity metrics concepts

Step-by-step walkthrough

  1. Compare the licensing and capacity options against the workload.

    Start with the business and technical requirements: user count, model size, refresh frequency, latency expectations, governance needs, data residency expectations, and any Fabric integration goals.     FYI — what changes when you move from shared to dedicated capacity.

    The important difference is not just licensing cost; it is operational control and workload isolation.

    • Pro focuses on standard sharing in shared capacity.
    • PPU brings some Premium-style features to individual users, but not a shared enterprise capacity for everyone.
    • Premium or Fabric capacity adds dedicated resources and unlocks features such as XMLA scenarios, larger models, paginated reporting, and capacity-level monitoring where validated.
  2. Review the XMLA endpoint path where it has been validated.
    1. In Power BI Service, open the workspace that would host the semantic model.
    2. Open Workspace settings and confirm the workspace is assigned to the validated license or capacity path needed for XMLA.
    3. If your admin has provided an XMLA endpoint, copy or note the server name or connection string.
    4. In an approved external tool, choose the connect-to-server option, paste the XMLA endpoint, authenticate, and open the semantic model metadata.
    5. Record whether the environment is read-only, read-write, or blocked pending tenant validation.

    If tools or capacity are unavailable, document XMLA use cases conceptually instead of forcing the connection.

    FYI — why the XMLA endpoint matters.
    XMLA is what lets approved external tools inspect or manage semantic model metadata instead of treating the model like a black box in the browser. That is important for enterprise ALM scenarios such as scripted deployments, advanced model edits, and deeper troubleshooting, which is why XMLA often becomes a deciding factor in capacity planning.
  3. Review paginated report fit where the environment supports it.
    1. If Power BI Report Builder is available, open it and create a blank paginated report.
    2. Add a data source and dataset that use approved sample data.
    3. Insert a table, add at least one parameter, and preview the report.
    4. Publish to a validated workspace only if licensing and workspace support are confirmed.
    5. Review export formats and note whether the pixel-perfect requirement justifies this report type.

    If Report Builder or workspace support is unavailable, keep this as a scenario discussion and record the blocker.

    FYI — why paginated reports are a separate decision from interactive reports.
    Paginated reports are designed for precise layout, repeating headers, multi-page printing, and export scenarios like invoice-style PDFs or operational detail dumps. If the requirement is "every row, exactly formatted, every time," a standard interactive Power BI report may be the wrong tool even if the data is the same.
  4. Review large semantic model requirements.
    1. In the Service, confirm which capacity or license the workspace uses today.
    2. Open the semantic model or workspace settings that expose size or storage behavior in your tenant.
    3. Review whether large semantic model storage format, memory limits, refresh duration, or XMLA workflows are relevant to the workload.
    4. Record every setting or constraint that still requires Azure Government validation.
    FYI — why model size planning is about memory, not just file size.
    Large semantic models affect refresh duration, in-memory footprint, and how much headroom the capacity has for concurrent report usage. That is why size-related decisions usually go together with incremental refresh, aggregations, model reduction, and capacity assignment rather than being treated as an isolated checkbox.
  5. Compare Direct Lake with Import and DirectQuery.

    Discuss the tradeoffs across freshness, modeling flexibility, fallback-to-DirectQuery behavior, operational complexity, and Azure Government readiness. If Direct Lake has not been validated, record Import mode plus refresh or aggregations as the default fallback path.

    FYI — why Direct Lake is not just "faster Import."
    Import mode gives the most mature modeling and predictable Power BI behavior, while DirectQuery trades speed for live-query access to the source. Direct Lake aims to reduce refresh movement by reading lake data more directly, but it adds new dependency and validation questions, so the architecture choice is really about operational fit and platform readiness, not only performance claims.
  6. Review OneLake, Lakehouse, and Warehouse as storage patterns.

    Document how each option would store data, how Power BI would consume it, what governance boundaries apply, and why these capabilities remain Commercial-focused or Verify for Gov until the target tenant confirms them.

    FYI — why the storage pattern changes governance responsibilities.
    Once reporting depends on shared lake or warehouse assets, BI teams are no longer governing only reports and semantic models; they also depend on upstream engineering, naming standards, security boundaries, and lifecycle controls in the storage platform. That is why a OneLake or Lakehouse decision usually involves more than the Power BI team alone.
  7. Review Semantic Link and autoscale as optional Fabric-era capabilities.

    Document how Semantic Link could expose semantic model metadata to notebooks and how autoscale could absorb temporary demand spikes on supported capacities. Mark both as Commercial-focused or Verify for Gov unless the target tenant has explicitly validated them, and record the non-Fabric fallback path.

    FYI — why autoscale and Semantic Link are optional, not day-one requirements.
    Autoscale can help with short bursts of demand, but it does not replace good model design or capacity sizing. Semantic Link can improve notebook-driven analysis against semantic models, but most core workshop outcomes still work without it, so both should be treated as acceleration features rather than blockers for initial deployment.
  8. Review capacity metrics and throttling signals.
    1. If the Capacity Metrics app is available, open it from the Apps list or the capacity administration entry point provided by your tenant.
    2. Select the relevant capacity or workspace scope.
    3. Review interactive workload, background workload, refresh pressure, memory consumption, and throttling indicators.
    4. Record the operational action each signal would trigger, such as optimization, workload redistribution, or scaling.

    If the app is unavailable, document which telemetry the admin team would need to provide instead.

    FYI — why capacity metrics matter even before users complain.
    CPU, memory, background refresh pressure, and throttling signals show whether the capacity is approaching a point where refreshes slow down or interactive reports become less responsive. Watching those patterns early lets you optimize datasets or rebalance workloads before the business experiences the problem as a "Power BI is slow" incident.
  9. Choose the Gov-safe fallback architecture.

    For any Fabric-specific or capacity-dependent feature that is still unvalidated, default to Import mode, well-designed aggregations, incremental refresh only where Service behavior is validated, and standard Power BI Service monitoring. Record exactly which advanced features are optional rather than required for day-one delivery.

  10. Document the final architecture recommendation.

    Write a short recommendation that states the selected licensing or capacity option, the assumptions behind it, the validation steps still required, known risks, the fallback path if a feature remains unavailable, and who must review the recommendation before it is finalized.

Azure Government note

Use the Gov-ready path by default. Features marked Verify for Gov or Commercial-focused require tenant, licensing, capacity, network, identity, or policy validation before hands-on delivery.
