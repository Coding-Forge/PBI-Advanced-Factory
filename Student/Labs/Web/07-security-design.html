Novice-friendly how-to guide

Create a static RLS role

  1. Select Modeling > Manage roles.
  2. Select New and name the role East Region.
  3. Select the territory table.
  4. Add a filter such as [TerritoryRegion] = "East".
  5. Save the role and test it with View as.

Create a dynamic RLS role

  1. Load the security mapping table.
  2. Create the relationship from the security table to the secured dimension.
  3. Open Manage roles and create Dynamic Territory Security.
  4. Filter the security table with [UserPrincipalName] = USERPRINCIPALNAME().
  5. Use View as with sample UPNs to confirm access.

Test roles

  1. Select Modeling > View as.
  2. Choose the role to test.
  3. For dynamic RLS, enter a sample user principal name.
  4. Record what data is visible and compare it to the expected mapping table.

Detailed step-by-step procedure

  1. Open the PBIP model.

    Confirm DimTerritory and FactSales exist and that territory filters flow to sales.

  2. Load security mapping files.

    Use Get data > Web for security-user-territory and security-role-matrix. Rename the mapping table SecurityUserTerritory.

  3. Create relationships.

    Relate SecurityUserTerritory[TerritoryKey] to DimTerritory[TerritoryKey]. Validate that filtering a territory filters sales.

  4. Create static RLS.

    Open Modeling > Manage roles. Create a role named East Region and filter DimTerritory to the East region or the matching territory keys.

  5. Create dynamic RLS.

    Create a role named Dynamic Territory Security. Filter SecurityUserTerritory with [UserPrincipalName] = USERPRINCIPALNAME().

  6. Test in Desktop.

    Use View as. Test the static role, then test the dynamic role by entering a synthetic UPN from the mapping file. Verify that only mapped territories are visible.

  7. Document expected access.

    Use security-role-matrix to record which personas should see which territories and whether Build permission is intended.

  8. Test in Service where available.

    Publish to a training workspace, assign users or groups to roles, and test as role. If Service access is unavailable, document this as a validation gap.

  9. Review Build permission.

    Explain who can build thin reports or Analyze in Excel from the semantic model. Document the risk of granting Build too broadly.

  10. Review optional controls.

    Keep OLS, sensitivity labels, Purview, external sharing, and B2B as Verify for Gov unless validated in the customer tenant.

Answer key

Show RLS filter expressions

Use these expressions in Manage roles. Exact table names must match your model.

// Static role option on DimTerritory
DimTerritory[TerritoryRegion] = "East"

// Static role option by territory keys
DimTerritory[TerritoryKey] IN { "T01" }

// Dynamic role filter on SecurityUserTerritory
SecurityUserTerritory[UserPrincipalName] = USERPRINCIPALNAME()

// Useful test UPNs
alex.manager@contoso.example     // T01, T02
casey.lead@contoso.example       // T03
devon.director@contoso.example   // T01, T02, T03, T04
jordan.rep@contoso.example       // T04
