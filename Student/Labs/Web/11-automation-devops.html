Lab 11 - PBIP lifecycle

Automation and DevOps

Use PBIP and git as the source-control foundation, then review external tools, APIs, service principals, Fabric Git integration, and conceptual CI/CD.

DevOpsDeliverable: Deployment checklistPBIP-first

What you will produce

  • Lifecycle goals
  • PBIP source review
  • Git workflow
  • Automation validation
  • Deployment checklist

Step-by-step walkthrough

  1. Define lifecycle management goals.

    Write down what “good” looks like for this project's delivery process before you change anything: repeatable builds, reviewable changes, a clear promotion path across environments, governance sign-off points, and a rollback plan if a release goes wrong. Also note that PBIP plus git is the source-of-record path for this workshop, while a .pbix file is only an output artifact when you explicitly need one.

    FYI — why lifecycle goals come first.
    Automation only helps when the team agrees on the release standard up front. If you do not define promotion, approval, and rollback expectations before building scripts or pipelines, you usually automate confusion and make failures harder to unwind.
  2. Open the PBIP repository and confirm what is source-controlled.
    1. Open the workshop repository containing the PBIP project you completed through Lab 10, in File Explorer or VS Code.
    2. Locate the project's .pbip file, then locate the matching .Report and .SemanticModel folders beside it.
    3. Confirm the folder you plan to commit contains text-based PBIP assets, not a standalone .pbix file acting as the source of record.
    4. If a .pbix exists, treat it as a generated output you create only when needed for packaging or handoff.
    FYI — why PBIP is better for source control than .pbix.
    A PBIP project breaks the report and semantic model into text files such as report.json, model.tmdl, and table definitions, so git can show exactly what changed. A single .pbix behaves more like a packaged artifact: good for opening or handing off, but much harder for a team to diff, review, merge, and troubleshoot.
  3. Inspect the PBIP file structure.
    1. Open .Report/definition and review the pages, report.json, and bookmarks content.
    2. Open .SemanticModel/definition and review the tables, relationships.tmdl, and model.tmdl files.
    3. Open one table .tmdl file and identify where columns, measures, and model metadata are stored as plain text.
    4. Note any generated or binary outputs you would avoid editing directly unless the lab explicitly requires it.
  4. Practice a basic git workflow on the PBIP project.
    1. Open a terminal at the repository root and run git status.
    2. Create a working branch with git checkout -b my-lab11-change.
    3. Make one small, low-risk change, such as editing a measure description, updating report text, or adding a simple page element.
    4. Run git status again to see which PBIP files changed.
    5. Run git diff and review the exact line-by-line changes before you stage anything.
    6. Stage only the intended files with git add <path>.
    7. Create a descriptive commit with git commit -m "Document lab11 PBIP change".
    FYI — why branches, diffs, and pull requests matter for PBIP.
    Even a small measure description or page-text change can affect training content, report behavior, or deployment packaging. Using a branch plus git diff lets you prove exactly what changed before the commit, and a pull request gives another reviewer a safe checkpoint before those PBIP files become the new source of record.
  5. Review pull request, release, and rollback expectations.

    List what a reviewer should check before approving a Power BI pull request: model and relationship changes, new or modified measures, data source connection strings, parameters, RLS role definitions, report page changes, unexpected auto-generated diffs such as GUID churn, release notes, version tags, and clear evidence that the change can be rolled back if needed.

  6. Review Tabular Editor and ALM Toolkit only if they are approved.
    1. If External Tools are approved in your environment, open the PBIP project in Power BI Desktop.
    2. Click External Tools > Tabular Editor to inspect tables, measures, and model metadata, then save only approved metadata changes.
    3. If you need to compare model versions and the tool is approved, launch ALM Toolkit, compare the source and target semantic models, and review the generated change script before you apply anything.
    4. If either tool is not approved, document the XMLA endpoint access, workstation software approval, tenant settings, and customer policy sign-off required before using it.
    FYI — why external tools are powerful but controlled.
    Tabular Editor and ALM Toolkit work directly against semantic model metadata, which is why they are so valuable for bulk edits, comparisons, and deployment scripts. That same power means they can bypass the slower safety of manual clicks in Desktop, so XMLA access, tenant settings, and approval boundaries matter before you let them touch production content.
  7. Review REST API deployment options.

    Identify the target workspace ID, the correct Power BI REST API or Fabric API cloud endpoint for your tenant, the authentication method you would use, and which operations you would automate such as import, export, or refresh. Keep the API path conceptual in this lab unless endpoint, permission, and policy validation are already complete.

  8. Review PowerShell administration requirements.

    Document which PowerShell modules are approved, such as MicrosoftPowerBIMgmt, confirm the correct cloud endpoint for your tenant, note the admin permissions required for tenant-level cmdlets, and list a few example administration tasks such as listing workspaces or triggering a refresh.

  9. Review service principal requirements.

    Document the Entra ID app registration, tenant-admin approval, security-group scoping, workspace role assignment, and secure secret or certificate storage required before a service principal can be used for automation. Do not treat “all users” access or plain-text secret storage as acceptable.

    FYI — why service principals are the usual automation identity.
    A pipeline or script needs a non-human identity that can keep working when a developer is offline, leaves the project, or has MFA prompts. A scoped service principal gives you that machine identity without tying deployments to one person's account, but only if you keep its permissions narrow and its secret or certificate storage secure.
  10. Review Fabric workspace Git integration if your tenant exposes it.
    1. Open the target workspace in the Power BI Service or Fabric portal.
    2. Open Workspace settings > Git integration.
    3. If the feature is available, connect the workspace to the approved repository, branch, and folder, then review how incoming changes, outgoing changes, sync status, and conflicts are displayed.
    4. If the feature is unavailable or unapproved, record that the fallback path for this workshop is the local PBIP-plus-git workflow you already practiced.
  11. Review conceptual CI/CD stages.

    Walk through the order of a conceptual Azure DevOps or GitHub Actions pipeline: validate PBIP content, package the release, authenticate with an approved identity, deploy with the correct API, apply environment-specific configuration, run smoke tests, and store logs or screenshots as audit evidence. Azure DevOps and GitHub Actions stay in the Verify-for-Gov bucket until endpoints, identities, runners, network paths, and tenant policy are validated.

    FYI — why CI/CD is more than just deployment.
    The deployment step is only one stage in a healthy pipeline. Validation, environment-specific configuration, smoke tests, and saved evidence are what keep a Dev/Test/Prod release repeatable — otherwise automation can push the wrong connection, miss a broken semantic model, or leave no proof of what was released.
  12. Validate Azure Government boundaries for every automation option.

    For PBIP, external tools, REST APIs, PowerShell, service principals, Fabric Git, and CI/CD, record the allowed cloud endpoint, identity authority, network path, tenant settings, and customer policy constraints. Do not rely on any Verify-for-Gov or Commercial-focused feature until those checks are complete.
