Novice-friendly how-to guide

Review PBIP source structure

  1. Open the PBIP project folder in File Explorer or VS Code.
  2. Locate the .pbip file.
  3. Locate the .Report and .SemanticModel folders.
  4. Open JSON or TMDL files as text to understand what is source-controlled.
  5. Do not edit generated files unless the lab explicitly tells you to.

Practice a basic git workflow

  1. Open a terminal at the repo root.
  2. Run git status.
  3. Create or switch to the working branch chosen for the lab.
  4. Make a small documented change.
  5. Run git diff to review it.
  6. Commit only the intended files.

Validate automation boundaries

  1. Identify endpoint, identity, network, tenant setting, and permission requirements.
  2. Mark REST APIs, PowerShell, service principals, XMLA, Fabric Git, and CI/CD as Verify for Gov unless approved.

Detailed step-by-step procedure

  1. Define lifecycle management goals.

    Document repeatability, reviewability, environment promotion, governance, and rollback expectations for Power BI delivery.

  2. Open the repository.

    Confirm the Power BI work is being done in PBIP format and that PBIX is not the source of record.

  3. Inspect PBIP structure.

    Review report and semantic model folders. Identify files that represent report definitions, model metadata, relationships, measures, and data sources.

  4. Practice a git workflow.

    Create a feature branch, make a small metadata or report change, run git status, review the changed files, and commit with a clear message.

  5. Discuss pull request and release review.

    Identify what reviewers should check: model changes, measures, data sources, parameters, RLS, report pages, unintended generated changes, release notes, tags, and rollback evidence.

  6. Review Tabular Editor and ALM Toolkit.

    If approved, demonstrate model inspection or comparison. If not approved, document required XMLA, workstation, customer policy, and tenant validations.

  7. Review REST API deployment options.

    Identify target workspace, cloud endpoint, permissions, import/export/refresh operations, and tenant settings. Keep hands-on API deployment optional until validated.

  8. Review PowerShell administration.

    Identify approved modules, endpoint configuration, required permissions, and common administration commands. Record endpoint and cloud validation.

  9. Review service principal requirements.

    Document app registration, admin setting approval, security group scoping, workspace role, and secret/certificate storage.

  10. Review Fabric Git integration.

    If available, discuss workspace-connected git, branch and folder selection, sync status, conflict behavior, and Commercial/Gov caveats. If unavailable, use local PBIP plus git as the Gov-safe path.

  11. Review CI/CD concepts.

    Walk through the Azure DevOps and GitHub Actions conceptual pipelines. Identify validation, package, authentication, deployment, configuration, smoke test, and evidence stages.

  12. Validate Azure Government boundaries.

    Record endpoint, identity, network, customer policy, and feature availability requirements before relying on automation.

  13. Complete deployment checklist.

    Record source control, model/report validation, environment configuration, automation validation, Azure Government validation, release evidence, and rollback path.

Azure Government note

Use the Gov-ready path by default. Features marked Verify for Gov or Commercial-focused require tenant, licensing, capacity, network, identity, or policy validation before hands-on delivery.
