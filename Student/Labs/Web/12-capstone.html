Novice-friendly how-to guide

Work through each lab step

  1. Start from the stated starter PBIP or completed prior module solution.
  2. Create or modify one object at a time using the exact names in the lab.
  3. Save after each major change.
  4. Validate the result in a simple visual, Service page, checklist, or evidence table before moving on.

Document validation

  1. Record the feature or setting being tested.
  2. Record expected behavior before testing.
  3. Capture actual behavior after testing.
  4. Mark tenant-dependent features as Verify for Gov if they cannot be validated hands-on.

Detailed step-by-step procedure

  1. Prepare the PBIP project.

    Open or create the capstone PBIP project in pbi-local\. Confirm it is source-controlled and using the raw GitHub CSV sources or approved alternatives.

  2. Build the semantic model.

    Create fact and dimension tables, relationships, role-playing dates, and segment/security tables. Hide technical columns and document model grain.

  3. Create the measure layer.

    Add base measures, time intelligence, variance, ranking/Top N, dynamic titles, and any scenario measures required by the report.

  4. Build the report experience.

    Create executive, analyst, and detail pages. Add drillthrough, tooltip page, bookmarks, navigation, conditional formatting, mobile layout, and accessibility review.

  5. Configure security.

    Create static and dynamic RLS, test roles in Desktop, and document expected versus actual results. Test in Service if available.

  6. Optimize and validate.

    Use Performance Analyzer, check model/cardinality issues, review DAX readability, and document before/after observations for any optimization.

  7. Publish and package.

    Publish where a training workspace is available. Configure refresh/credentials, document gateway requirements, and package the report as an App where available.

  8. Govern and operate.

    Complete the endorsement checklist, operations runbook, usage/refresh review, access model, support ownership, and escalation path.

  9. Add optional extensions only when validated.

    Fabric, Direct Lake, OneLake, Copilot, AI visuals, deployment pipelines, APIs, service principals, XMLA, and capacity metrics must be validated before hands-on use.

  10. Submit evidence.

    Submit PBIP source, rubric, screenshots/notes, RLS test evidence, refresh/App/governance evidence, operations runbook, and Azure Government readiness notes.

Azure Government note

Use the Gov-ready path by default. Features marked Verify for Gov or Commercial-focused require tenant, licensing, capacity, network, identity, or policy validation before hands-on delivery.
