Lab 12 - Enterprise-ready solution

Capstone

Bring together modeling, DAX, report UX, performance, security, Service deployment, governance, monitoring, and lifecycle management.

Applied capstoneDeliverable: Validated solution packagePower BI file

What you will produce

  • Power BI source file
  • Optimized model and DAX
  • Interactive report experience
  • RLS-secured deployment
  • Governance and operations evidence

Step-by-step walkthrough

  1. Confirm your capstone starting point and save your Power BI file.
    1. Start from your completed Lab 1-11 workshop solution — the same Power BI file you have been building throughout the workshop.
    2. Open the file in Power BI Desktop and confirm it is fully up to date with everything you completed through Lab 11.
    3. If you created a new working copy for the capstone, save it into the workshop repository before making changes.
    4. Plan to complete one milestone at a time: semantic model, DAX, report UX, security, Service deployment, governance, monitoring, and evidence packaging.
    FYI — why the capstone is validation-focused.
    This lab is meant to prove that the model, DAX, UX, security, and deployment practices from Labs 1-11 work together as one solution. Real projects rarely fail because a team never learned one more feature; they fail because nobody checked that the finished deliverable still works end to end after all the pieces were combined.
  2. Validate the semantic model.
    1. Open Model view and confirm your solution uses fact and dimension tables with the same naming and grain conventions established in Lab 1.
    2. Create or finish any missing relationships explicitly, then verify filter direction and cardinality before you move on.
    3. Hide technical columns and key fields that should not appear in the report authoring experience.
    4. Document the model grain and label any Gov-sensitive feature as Gov-ready, Verify for Gov, or Commercial-focused.
    FYI — why model grain and relationships are an early quality gate.
    If the semantic model is wrong, every visual and measure built on top of it can still look polished while returning bad numbers. Confirming relationship direction, cardinality, and grain before you move on is the fastest way to prevent later DAX or report bugs that are really model-design problems.
  3. Validate the advanced DAX layer.
    1. Create or review the base measures such as Sales Amount, Gross Margin, Gross Margin %, and Quantity.
    2. Add or verify time-intelligence measures such as YTD, prior-year, and YoY % results.
    3. Add or verify target variance, ranking or Top N logic with RANKX, and any dynamic title or measure-switching logic.
    4. Validate the totals for every important measure at the customer, product, territory, and date grain before you continue.
    FYI — why DAX validation happens at multiple grains.
    A measure can appear correct on a card and still be wrong by customer, product, territory, or date because of context mistakes. Checking totals at several grains is how you catch issues with time intelligence, ranking, or variance logic before those errors get repeated across the final report.
  4. Validate the report experience.
    1. Build or review the Executive Summary and Analyst Exploration pages.
    2. Create or confirm a detail Drillthrough page and a report page Tooltip page using the patterns from Lab 4.
    3. Add at least one bookmark-driven interaction, such as show/hide or reset, and pair it with consistent navigation buttons.
    4. Apply conditional formatting tied to a documented threshold, then complete the mobile layout and accessibility checks for alt text, tab order, contrast, and visual titles.
  5. Validate security.
    1. Import or create the security mapping table you need for role-based filtering.
    2. Open Modeling > Manage roles and create a static RLS role plus a dynamic RLS role that uses USERPRINCIPALNAME().
    3. Open Modeling > View as and test both roles in Desktop.
    4. If a training workspace is available, publish and test the same roles in the Service, then document who should receive Build permission and why.
    FYI — why RLS must be retested after changes.
    Row-level security is not a one-time setup task. New measures, new relationships, or a new mapping table can change how filters flow, so testing both Desktop View as and Service behavior is what proves users will only see the rows they are supposed to see after the full capstone solution is assembled.
  6. Publish and distribute the solution.
    1. In Power BI Desktop, click Home > Publish and choose the approved training workspace if Service access is available.
    2. In the Service, configure semantic model credentials and scheduled refresh, or document the gap if workspace access is not part of your learner environment.
    3. Record any gateway requirement, or explicitly note why no gateway is needed for the approved workshop data path.
    4. Create or review the Power BI App audience, then document the intended consumers and the workspace roles they should hold.
    FYI — why publish, refresh, and audience checks are part of the solution.
    A polished report is not finished if credentials fail, refresh never runs, or the wrong audience receives access. Validating workspace roles, App audience, refresh settings, and gateway requirements is what turns a good Desktop file into a usable production-style deliverable.
  7. Complete governance and operations checks.
    1. Finish the endorsement readiness checklist covering ownership, refresh reliability, security, data quality, and support evidence.
    2. Draft a short operations runbook with refresh ownership, failure response, and support or escalation contacts.
    3. If Service telemetry is available, review usage metrics and refresh history and record any follow-up actions.
    4. Document the support owner, business owner, and escalation path for the capstone solution.
  8. Review optional enhanced extensions only after validation.

    Optional Fabric workspace Git integration, Direct Lake, OneLake, Lakehouse or Warehouse features, Copilot or AI-assisted authoring, deployment pipelines, REST API automation, service principals, XMLA read/write, external tools, and capacity metrics should be added only after tenant, licensing, policy, and cloud availability are validated. For every optional feature you attempt, record its availability status and the fallback path you used if it was unavailable.

  9. Complete the validation rubric and package the evidence.

    Use the rubric below as your final submission checklist. Record evidence as you go instead of waiting until the end.

    FYI — why evidence collection matters.
    In a real engagement, the final handoff is not just the Power BI file — it is also the proof that the team validated model quality, DAX results, security, publishing, and operational readiness. Capturing screenshots, notes, and rubric evidence as you go prevents last-minute guesswork and gives reviewers something concrete to sign off on.

Azure Government note

Use the Gov-ready path by default. Features marked Verify for Gov or Commercial-focused require tenant, licensing, capacity, network, identity, or policy validation before hands-on delivery.
