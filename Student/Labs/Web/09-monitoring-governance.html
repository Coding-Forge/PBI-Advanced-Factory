Lab 9 - Operate and support

Monitoring and Governance

Monitor adoption, troubleshoot refresh, review tenant settings, inspect gateways, and document support operations.

OperationsDeliverable: Operations runbookPower BI file

What you will produce

  • Usage and adoption review
  • Refresh troubleshooting
  • Tenant setting notes
  • Operations runbook

Step-by-step walkthrough

  1. Start from the content published in Lab 8.

    Use the report and semantic model already published to the Power BI Service. If you do not have direct workspace access in this environment, follow the instructor demo or screenshots and still complete the operational notes as a conceptual exercise.

  2. Open usage metrics for the deployed report.
    1. In Power BI Service, open the workspace from Lab 8.
    2. Open the published report or App you want to review.
    3. Click the report More options menu (...) and choose Usage metrics report or View usage metrics.
    4. Review total views, unique viewers, recent activity, and page-level usage if those visuals are available.
    5. If the option is missing, record whether the blocker is permissions, licensing, tenant policy, or environment scope.
    FYI — what usage metrics are really telling you.
    Usage metrics are an adoption signal, not a quality guarantee. They help you see whether a report is being opened, which pages are being used, and whether engagement is growing or fading, but they do not explain why people behave that way unless you combine them with stakeholder feedback and support history.
  3. Interpret the adoption signals.

    Record at least one high-use signal, one low-use or declining-use signal, and the follow-up action each pattern suggests. Tie the observation to a real support or governance action such as training, report retirement review, navigation cleanup, or added owner follow-up.

    FYI — why adoption review is an operations task.
    A heavily used report may justify more rigorous support, performance tuning, and owner coverage because business decisions depend on it. A low-use report can indicate poor discoverability, confusing design, duplicate content, or a report that should be retired, which is why monitoring adoption is part of governance rather than just curiosity.
  4. Review semantic model refresh history.
    1. Return to the workspace.
    2. Locate the semantic model, open its More options menu (...), then click Settings.
    3. Open Refresh history or the refresh history section on the settings page.
    4. Record the most recent refresh status, duration, and failure details if present.
  5. Check credentials, privacy, and source mapping clues.
    1. On the same settings page, expand Data source credentials.
    2. Review the credential owner, authentication state, and privacy levels.
    3. Check whether a gateway or cloud connection is referenced for the semantic model.
    4. Document the likely next action for the current state, but do not change production credentials or schedules without approval.
    FYI — why refresh troubleshooting usually starts here.
    Many refresh failures are not caused by the DAX model at all; they trace back to expired credentials, ownership changes, mismatched privacy settings, or a missing gateway/cloud mapping. Looking at the credential owner and connection path first helps you separate data-access problems from actual model or source-data issues.
  6. Review tenant settings that affect governance.
    1. If you have admin access, click the Settings gear in the Service header, then click Admin portal.
    2. Open Tenant settings.
    3. Review the settings that control sharing, export, publish to web, certification or endorsement, external guest access, and Build permissions.
    4. Record which settings are enabled, limited to specific security groups, or left for customer policy decisions.

    If you do not have admin access, use the instructor walkthrough or screenshots and note that the review was conceptual.

    FYI — why tenant settings are often group-scoped instead of simply on or off.
    Settings like Publish to web, external sharing, export, and certification can create real compliance or data-loss risk if they are enabled for everyone. Limiting them to specific security groups lets the tenant allow approved use cases without making every workspace owner responsible for interpreting enterprise policy on their own.
  7. Inspect gateway health where a gateway is in use.
    1. If the semantic model uses a gateway, open Admin portal > Manage gateways or the gateway management page available in your tenant.
    2. Select the gateway cluster and confirm whether it is online.
    3. Review the configured data sources, stored credential owner, and gateway version.
    4. Record the support owner and escalation path if the gateway goes offline or loses a data source mapping.

    If no gateway is used in this lab, state that the current workshop sources are cloud or public and that gateway monitoring is a future-state requirement.

    FYI — why gateway monitoring matters even when the report design is fine.
    A gateway is the runtime bridge between the Service and restricted data sources. If the cluster is offline, outdated, or mapped to the wrong source credentials, every scheduled refresh that depends on it can fail even though the report and semantic model were authored correctly.
  8. Review optional admin signals and note their blockers.
    1. Check whether Activity logs, Audit logs, the Admin monitoring workspace, Capacity metrics, Microsoft Purview, and DLP policies are available to your role.
    2. For each feature you can open, capture the specific evidence it provides for monitoring or governance.
    3. For each feature you cannot open, record the admin permission, license, tenant, or cloud-validation blocker.

    These optional admin capabilities should remain marked Verify for Gov unless your tenant has already validated them.

    FYI — why these admin signals complement each other.

    Each tool answers a different governance question, so one view rarely replaces the others.

    • Activity or Audit logs help answer who did what and when.
    • Capacity metrics help explain whether workload pressure is causing slowdowns or throttling.
    • Purview and DLP focus on classification, protection, and policy enforcement rather than adoption.
  9. Complete the operations runbook.

    Use the runbook structure below so content inventory, ownership, monitoring, and incident response details are captured consistently.

    Runbook areaFields to completeSource
    Content inventoryWorkspace, App, report, semantic model, source file pathService and repository.
    OwnershipBusiness owner, technical owner, support contactProject governance.
    Adoption trackingUsage pattern, training need, support signal, retirement candidate, follow-up ownerUsage metrics, App metrics, support queue, stakeholder feedback.
    Data sourcesSource type, gateway required, credential ownerSemantic model settings.
    RefreshSchedule, duration, recipients, retry pathRefresh settings/history.
    AccessWorkspace roles, App consumers, Build, RLS/OLSWorkspace/App/model settings.
    Monitoring cadenceUsage, refresh, gateway, capacity, compliance, owner review rhythmOperations model.

    FYI — why a runbook is part of governance.
    The runbook turns scattered knowledge in the Service, repository, and support queue into a repeatable operating model. When ownership changes or an incident happens, the runbook is what keeps refresh troubleshooting, access requests, and escalation paths from depending on one person's memory.
  10. Define the support process.

    Write down who handles refresh failures, access requests, data quality issues, performance complaints, enhancement requests, and adoption follow-up. If the training environment does not have named owners, record the responsible role or the escalation path you would expect in production.

  11. Document the remaining validation gaps.

    For every feature you could not access directly, write down the exact gap, the role that would need to validate it in a real deployment, and whether the item is blocked by licensing, tenant policy, admin permissions, or Azure Government feature availability.

Azure Government note

Use the Gov-ready path by default. Features marked Verify for Gov or Commercial-focused require tenant, licensing, capacity, network, identity, or policy validation before hands-on delivery.
